# 客服工单分派与时效质检

把客服系统导出的**工单表**和当班的**坐席表**交给它，它会按贵司的规则把每张工单分好类、定好优先级、合并掉重复反映的单，按工作日历算清楚首次响应和解决有没有超时，再按坐席负载把未结工单派出去，超时和派不出去的升级给对应负责人，最后出一份时效达标统计。

结论里的数字（张数、达标率、超时数）全部由程序算出；大模型只负责给需要优先回复的客户写回复草稿，不改任何数字。没有配置大模型时，照样办结，只是没有草稿。

---

## 一、需要哪些材料

### 1. 工单表（必需）

从客服系统（智齿、Udesk、美洽、Zendesk、自研工单系统等）导出的工单明细，一行一张工单。列名不必和下面一字不差，括号里是能认出来的别名：

| 标准列 | 必需 | 能认的写法 | 说明 |
| --- | --- | --- | --- |
| 工单号 | 是 | 工单编号、单号、ticket id、编号 | 不能重复；重复的那行不参与计算 |
| 客户 | 是 | 客户名称、用户账号、会员号、customer | 用来判断同一客户的重复单和反复来电 |
| 创建时间 | 是 | 提交时间、进线时间、受理时间、created | 计时起点，看不懂的工单不参与时效 |
| 首次响应时间 | 否 | 首响时间、首次回复时间、first response | 没有这列时，未结单按「还没响应」计 |
| 解决时间 | 否 | 关闭时间、完结时间、结单时间、resolved | 没有这列时，已结单的解决时效记为「缺解决时间」 |
| 渠道 | 否 | 来源、进线方式、channel | 电话、微博等渠道可以提优先级 |
| 客户等级 | 否 | 会员类型、客户类型、VIP、tier | VIP 等可以提优先级 |
| 标题 | 二选一 | 主题、摘要、subject | 分类主要看标题 |
| 内容 | 二选一 | 描述、详情、问题说明、description | 标题没命中时看内容 |
| 状态 | 否 | status | 含「已解决/已关闭/已完成/完结/结单」或 resolved/closed 视为已结 |
| 处理人 | 否 | 受理人、负责人、跟进人、assignee | 已有处理人的未结单默认沿用 |

时间支持这些写法：`2026-10-12 09:30`、`2026/10/12 9:30`、`2026-10-12T09:30:00`、`2026年10月12日 9:30`。只有日期没有钟点的，按当天 00:00 计。

**状态判断**：状态为空但有解决时间的，按已结处理；状态写着「合并」「重复单」的，按已结处理。

### 2. 坐席表（必需）

当班坐席名单，一行一人：

| 标准列 | 必需 | 能认的写法 | 说明 |
| --- | --- | --- | --- |
| 坐席 | 是 | 客服、姓名、员工、agent | 重名只保留第一行 |
| 技能组 | 是 | 组别、队列、技能、group | 一人多组用竖线、顿号或逗号分隔，例如「账务组、综合组」 |
| 在岗 | 否 | 在线、上班、当班、状态 | 是/在岗/在线 = 在岗；否/离岗/休息/请假/下线 = 不在岗；空着按「读入坐席」步骤的 `defaultOnDuty` |
| 当前待办 | 否 | 在手、未结、当前工单、backlog | 坐席手上已有的单数，分派时算进负载 |
| 上限 | 否 | 容量、最大、最多、capacity | 同时最多处理多少张；空着按 `defaultCap` |

技能组的名字要和「问题分类」步骤里每一类的 `group` 对得上，否则那一类工单会派不出去（分派表里会写明「坐席表里没有某某组的人」）。

### 3. 下载模板

导入面板里可以下载两份模板，表头就是上面的标准列，模板里的几行只是格式示例，**请换成贵司真实导出的数据再办理**。

## 二、处理流程（每一步做什么、规则在哪改）

技能是一串有先后的处理步骤，后一步用前一步的结果。删掉某一步，后面依赖它的结果就会变（比如删掉「合并重复」，重复单就会各自计时、各自分派）。

### 1. 读入工单 `__ticket_intake__`

- 按上面的列规格读工单表，统计总数与未结数。
- `maxRows`：单次最多处理多少张，超过就停下请分批导入。
- 材料里缺「首次响应时间」或「解决时间」列时，会在这一步明确告诉您，相关时效按未发生处理。

### 2. 读入坐席 `__ticket_agents__`

- 统计在岗人数、各技能组人数、还能接多少张（上限 − 当前待办）。
- 一个在岗坐席都没有时直接停下（`guard: fail`），因为后面没法分派。
- `defaultCap`、`defaultOnDuty`：坐席表缺列时的默认值。

### 3. 检查数据 `__ticket_validate__`

逐张检查：

- 缺工单号；
- 工单号与前面某行重复；
- 创建时间缺失或看不懂；
- 首次响应早于创建、解决早于创建、解决早于首次响应；
- 标题和内容都为空。

前四类问题的工单**不参与后续计算**（在明细里标「数据有误」）。这类工单占比超过 `maxBadRatio`（默认 10%）时整单停下，请先修材料——这通常说明导出时选错了字段或时间格式被 Excel 改坏了。

### 4. 工作日历 `__ticket_calendar__`

- `workStart` / `workEnd`：每天的服务时间。时效只在服务时间里走表，晚上和休息日不计时（P1 除外，见第 8 步 `allDay`）。
- `workdays`：每周哪几天上班，1=周一 … 7=周日。7×12 小时客服写 1～7。
- `holidays`：节假日不计时。默认填的是 2026 年法定节假日，**请按贵司实际排班核对**；节假日照常服务的客服中心请清空。
- `extraWorkdays`：调休上班日，即使是周末或在 holidays 里也计时。
- `asOf`：统计截至的时刻。`latest` 表示取材料里最晚的一个时间（创建/响应/解决里最大的），这样同一份材料无论什么时候办理结果都一样；要按某个时点质检就写具体时间，例如 `"2026-10-12 18:00"`。

### 5. 问题分类 `__ticket_classify__`

- 每一类有：名称 `name`、负责的技能组 `group`、默认优先级 `priority`（1～4）、关键词 `keywords`。
- 打分：标题里出现一个关键词记 `titleWeight` 分（默认 2），内容里出现记 1 分；分数最高的类胜出，同分取写在前面的类。
- 一个关键词都没命中的，归入 `defaultCategory`，交给 `defaultGroup`，优先级 `defaultPriority`。
- 明细表的「说明」列会写出命中了哪些词，方便您调词典。

**怎么调**：看明细里「其他咨询」占比，如果偏高，把这些单的高频说法加进对应类的 keywords；如果某类被误判，把太宽泛的词（例如「问题」）删掉，或把更具体的类挪到前面。

### 6. 定优先级 `__ticket_priority__`

在分类给出的默认优先级上调整（数字越小越急，最高 P1、最低 P4）：

1. `urgentKeywords`：标题或内容命中任一词，**直接定 P1**，不再叠加其他调整。用于盗刷、诈骗、媒体曝光、监管投诉、大面积故障这类必须马上处理的情况。
2. `levelBoost`：客户等级里包含这些字就提相应级数，例如 `VIP: 1`。
3. `channelBoost`：渠道里包含这些字就提相应级数，写负数表示降级。
4. `repeatContact`：同一客户在材料里有 `count` 张及以上工单，再提 `boost` 级——反复来找说明问题没解决。

明细表「说明」列会逐条写出优先级是怎么来的，例如「支付扣款默认 P2；VIP客户提 1 级」。

### 7. 合并重复 `__ticket_dedupe__`

同一个客户为同一件事反复提单，如果各算各的，会让超时数虚高、也会让几个坐席同时处理一件事。合并规则：

- 同一客户；
- `sameCategory: true` 时还要求同一类问题；
- 后一张的创建时间在前一张之后 `windowHours` 小时以内；
- 标题相似度（二元字组 Jaccard）≥ `similarity`，标题为空时用内容前 40 个字比。

满足条件的后一张并入最早那张（主单）：

- 主单取两者中更高的优先级；
- 被并入的单还没结、而主单已结时，主单重新打开（客户还在追问）；
- `closeMerged: true` 时被并入的单按已结处理，只跟进主单。

合并结果在「重复合并表」，每行写明相似度和间隔时间，您可以据此调阈值：误合并多就调高 `similarity`，漏合并多就调低。

### 8. 计算时效 `__ticket_sla__`

`targets` 按优先级设时限：

- `firstResponseMinutes`：从创建到首次响应，最多多少分钟（服务时间内）；
- `resolveHours`：从创建到解决，最多多少小时（服务时间内）；
- `allDay: true`：这一级不看工作日历，7×24 小时计时（默认只给 P1）。

计算口径：

- 已响应的单：用时 = 创建到首次响应之间落在服务时间里的分钟数，超过时限记「超时」，否则「达标」。
- 未响应的未结单：用时 = 创建到统计时刻，超过时限记「未响应·已超时」，没超记「未响应·计时中」。
- 已结但没有响应时间的单：用解决时间代替首次响应；两者都没有的记「已结·缺响应时间」，不参与达标率。
- 解决时效同理；已结但没有解决时间的记「已结·缺解决时间」，不参与达标率。
- 截止时刻（解决时限）按服务时间往后数出来，例如周五 20:00 创建的 P3 单，时限 36 小时，会跨过周末顺延。

没给某一级设时限时，按首响 4 小时、解决 72 小时计，并在这一步明确提示。

### 9. 临期预警 `__ticket_risk__`

只看未结单：

- 已超时：解决用时超过时限，或者还没首次响应且首响已超时；
- 临期：解决用时达到时限的 `riskRatio`（默认 80%），或者还没响应且首响用时达到 80%。

### 10. 分派坐席 `__ticket_assign__`

先把未结单从急到缓排好：优先级高的在前 → 已超时的在前 → 临期的在前 → 剩余时间少的在前 → 创建早的在前。然后逐张分派：

- `keepExisting: true`：工单表里已有处理人的，沿用原处理人，并计入他的负载。
- 候选人：在岗、技能组包含这张单的处理组、`respectCap: true` 时手上待办 + 本次已派 < 上限。
- `strategy: least-load`：选「（待办 + 本次已派）÷ 上限」最小的人，同比例选单数少的，再相同按坐席表顺序。
- `strategy: round-robin`：组内按坐席表顺序轮流。
- `allowFallback: true`：本组没人可接时，转给 `fallbackGroup` 的人。
- 还是没人：标「未分派」并写明原因——坐席表里没有这个组 / 这个组没人在岗 / 这个组在岗的人都满额。

分派表按上面的急缓顺序列出，附「坐席负载」表：每人原有待办、本次新派、派后合计、上限、负载率。

### 11. 升级 `__ticket_escalate__`

按顺序取第一条命中的规则：

1. P1 且已超时 → `p1BreachTo`（默认值班经理）；
2. 已超时 → `breachTo`（默认客服主管）；
3. 派不出去且优先级不低于 `unassignedMaxPriority` → `unassignedTo`；
4. 临期且优先级不低于 `riskMaxPriority` → `riskTo`（默认组长）。

### 12. 时效质检 `__ticket_quality__`

按优先级（P1～P4 + 合计）和按处理组分别统计：

- 工单数（不含并入的重复单和数据有误的单）；
- 首响达标率 = 首响达标张数 ÷ 首响可判定张数；
- 解决达标率 = 解决达标张数 ÷ 解决可判定张数；
- 平均首响用时（只算已响应的单）；
- 未结数、未结已超时数。

「可判定」指已经有结果的单：已响应/已解决的，或者还没响应/解决但已经超时的。还在计时中的不算进分母，避免把刚进来的单当成达标。

`targets.firstResponseRate` / `targets.resolveRate` 是考核线，低于的维度会在结论和表里标「未达标」。

### 13. 保底检查 `__ticket_capacity_guard__`

- 派不出去的 P1 超过 `maxUnassignedP1`（默认 0）时停下，提示马上加派人手——这时候发出去的分派表是不完整的。
- `maxUnassigned` 限制全部派不出去的张数，-1 表示不限。
- 想只提醒不拦截，把 `guard` 改成 `warn` 并去掉 `failFast`。

### 14～18. 交付表格

| 步骤 | 表 | 内容 |
| --- | --- | --- |
| `__ticket_deliver_detail__` | 工单处理明细 | 每张单一行：分类、处理组、优先级、状态、首响/解决用时与结论、解决时限、风险、处理人、升级给谁、说明（命中词、优先级依据、分派原因） |
| `__ticket_deliver_assign__` | 分派表 + 坐席负载 | 未结单按急缓排序的处理人与剩余时间；每位坐席派后负载 |
| `__ticket_deliver_escalation__` | 升级清单 | 需要升级的单、升给谁、原因 |
| `__ticket_deliver_quality__` | 时效达标统计 + 各组时效 | 按优先级和按组的达标率 |
| `__ticket_deliver_merge__` | 重复合并表 | 主单、并入单、相似度、间隔 |

哪一步不在技能里，文书里就没有那张表。每张表都可以单独下载成 CSV。

### 19. 结论 `__ticket_report__`

汇总成一句话：总单数、未结、合并、已分派/派不出去、超时未结、临期、升级、首响与解决达标率。同时把「需要先回复的工单」（`draftFor` 里的优先级、未结、按急缓排序前 `maxDrafts` 张）整理给下一步。

### 20. 回复草稿 `__llm_product_brief__`

- 用已配置的大模型，按 `role` / `task` 给上一步挑出来的工单逐张写回复草稿。
- `lockNumbers: false`：这是写给客户的话，不要求复述统计数字；但工单号、时间、处理人只能照抄程序给的事实。
- `keepEngineLine: true`：办结说明 = 程序结论 + 草稿，结论不会被模型的话替换。
- 没配置大模型：这一步跳过，办结说明只有程序结论。
- 配置了但调用失败：这一步报错并停下，界面会写明原因（不会假装成功）。

## 三、常见调整示例

**7×24 小时客服**：`workdays` 写 1～7，`workStart: "00:00"`，`workEnd: "24:00"`，清空 `holidays`。

**只做质检、不分派**：删掉「分派坐席」「升级」「保底检查」「分派表」「升级清单」这几步；坐席表仍需导入（读入坐席是第 2 步），也可以把「读入坐席」一并删掉。

**按组轮流派单**：`strategy: round-robin`。

**投诉单一律 P1**：在「问题分类」里把投诉类 `priority` 改成 1，或把「投诉」加进 `urgentKeywords`。

**VIP 提两级**：`levelBoost` 里写 `VIP: 2`。

**合并更严格**：`similarity` 调到 0.7，`windowHours` 调到 24。

**节假日也算时效**：清空 `holidays`。

改完先在技能页「用材料试跑」，用同一份工单表对比改前改后：哪些单的优先级、处理人、超时结论变了，一目了然。

## 四、停下来的情况

| 停在哪一步 | 原因 | 怎么办 |
| --- | --- | --- |
| 读入工单 / 读入坐席 | 还没导入材料 | 在对话里导入工单表和坐席表后点继续 |
| 读入坐席 | 坐席都不在岗 | 检查坐席表「在岗」列，或换当班名单 |
| 检查数据 | 有问题的工单占比过高 | 按明细里「数据有误」的行修正导出，常见是时间列被 Excel 改成了数字 |
| 保底检查 | P1 派不出去 | 加派在岗坐席，或把 P1 所属组的上限调高 |
| 回复草稿 | 大模型调用失败 | 看报错原因检查接入配置；结论与表格不受影响 |

步骤顺序被改乱（例如删了「读入工单」却保留「分派坐席」）时，会提示「这一步需要先完成某某步骤」。

## 五、口径说明

- 「现在」默认取材料里最晚的时间，不取服务器当前时间，所以同一份材料任何时候办理结果都相同，便于复核和版本对比。
- 服务时间按自然日切分，跨天的工单逐天累加服务时间内的分钟。
- 节假日与调休只影响非 `allDay` 的优先级。
- 并入的重复单不计入工单数、达标率和分派，但会出现在明细（状态「并入 某某」）和合并表里。
- 数据有误的单出现在明细里，不计入任何统计。
- 相似度用标题的二元字组计算，忽略空格和标点，对中文短标题效果较好；英文或很长的标题建议提高阈值。

# OwnAgent 战略发展方向（2026 Q4 – 2028）

> **文档性质**：战略规划 · 面向决策  
> **版本**：v1.0 · 2026-09-30  
> **适用范围**：`/work/ownagent` 产品线、Skill Gate CLI / Action / IDE 插件、作品集站点  
> **前置阅读**：`docs/ownagent-status.md`（现状与已知边界）

---

## 0. 执行摘要

**一句话定位**

> OwnAgent 是 **Agent 变更的因果门禁**：在 Skill 上线之前，用确定性结构因果模型（SCM）回答三个问题——**改动会让成功率掉多少（ΔP）、哪一步是根因（Pivotal Step）、能不能合并（PASS / WARN / BLOCK）**。

**核心判断**

1. Agent 行业的瓶颈正在从「能不能做出来」转向「敢不敢改」。模型、框架、RAG 都在快速商品化；**变更安全**还没有被定义成一个品类。
2. 传统软件有单元测试、CI、Code Review、灰度发布四道闸门；Agent 的 Skill / Prompt / Tool 链路几乎只有「人工试几句」一道。这是结构性缺口，不是功能缺口。
3. OwnAgent 已经具备别人不容易复制的内核——**确定性 do() 干预传播 + Pivotal Step 归因**。评测平台给的是「分数变了」，OwnAgent 给的是「为什么变、改哪一步」。

**三年目标**

| 阶段 | 时间 | 身份 | 标志性结果 |
|---|---|---|---|
| **Horizon 1 · 敢用** | 2026 Q4 – 2027 Q1 | 最好用的 Skill 发版检查工具 | 外部仓库把 `ownagent check` 设为 required check |
| **Horizon 2 · 嵌入** | 2027 Q2 – Q4 | Agent 团队的变更治理层 | 生产 trace 自动回流成回归集；事故复盘引用门禁报告 |
| **Horizon 3 · 定义** | 2028 | 「Agent Change Safety」品类的标准制定者 | 开放协议被第三方 Agent 平台实现 |

## 1. 战略论点（Thesis）

### 1.1 行业正在经历的转折

```
2023–2024        2025–2026              2027+
能力竞赛    →    工程化竞赛      →      治理竞赛
"能回答吗"       "能稳定跑吗"            "改了还稳吗、谁负责"
模型 / Prompt    框架 / RAG / Eval      变更安全 / 审计 / 归因
```

每一次软件范式成熟，最后留下来的高价值层都不是「生成」，而是「**控制**」：

- Web 时代：写代码的 IDE 很多，但 **CI / Code Review / Feature Flag** 成为基础设施
- 云原生时代：部署工具很多，但 **可观测性 / 策略即代码** 成为基础设施
- Agent 时代：Skill 编写工具会越来越多，**变更门禁** 将成为基础设施

### 1.2 为什么现有方案不够

| 现有做法 | 能回答 | 回答不了 |
|---|---|---|
| 人工对话试跑 | 「感觉还行」 | 覆盖面、可复现、可审计 |
| LLM-as-Judge 评测 | 「分数从 82 变 76」 | **为什么掉、掉在哪一步** |
| 结构 diff / Lint | 「改了哪几行」 | 改动的 **行为后果** |
| 线上 A/B | 「上线后变差了」 | 上线 **之前** 就拦住 |

OwnAgent 的独特位置：**上线前 × 因果级 × 可复现**。这个象限目前基本是空的。

### 1.3 我们押注的三个前提

1. **Skill 会成为 Agent 的基本交付单元**（类似函数之于程序、容器之于服务）。已有迹象：SKILL.md、MCP tool、可组合 workflow 的普及。
2. **企业需要可解释的「不许发」**，而不是一个分数。合规、事故追责、跨团队协作都要求「给出原因」。
3. **确定性优先于概率性**。在门禁场景下，可复现的 exact replay 比「跑 5 次取平均」更有说服力，也更便宜。

> 这三个前提若有一个被证伪，需要回到本节重新评估。见 §9 风险矩阵。

## 2. 定位与品类定义

### 2.1 品类：Agent Change Safety

我们不称自己为「评测平台」或「Agent 可观测性」，而是主动定义一个新品类：

> **Agent Change Safety**：在 Agent 能力（Skill / Prompt / Tool / 路由）变更进入生产之前，量化其行为后果、定位因果根因、执行发布策略的一类基础设施。

品类的三个关键词，也是我们要让用户自然说出口的词：

| 术语 | 含义 | 对应能力 |
|---|---|---|
| **ΔP** | 候选版相对基线的成功率差 | `consequenceDeltaForCompare` |
| **Pivotal Step** | 干预后能翻转 PASS/FAIL 的根因步骤 | `analyzePivotalSteps` |
| **Gate Verdict** | PASS / WARN / BLOCK 发布判定 | `releaseGate.ts` |

### 2.2 定位矩阵

```
                     因果级（为什么）
                           ▲
                           │
                           │     ◆ OwnAgent
                           │       （上线前 · 因果 · 确定性）
                           │
  上线后 ◄─────────────────┼─────────────────► 上线前
                           │
     ○ 可观测性平台          │     ○ 评测 / Eval 平台
       （上线后 · 现象）      │       （上线前 · 分数）
                           │
                           ▼
                     现象级（是什么）
```

### 2.3 我们是什么 / 不是什么

| 是 | 不是 |
|---|---|
| Skill 的 CI 与发布闸门 | 又一个 Chat / RAG 产品 |
| 因果归因引擎 | 通用 LLM 评测打分器 |
| 可嵌入的治理模块 | 大而全的 Agent 开发平台 |
| 开发者工作流的一部分（PR / IDE / CLI） | 需要单独登录才能用的孤岛 SaaS |

## 3. 护城河设计

护城河不是功能清单，而是 **随时间变深、竞争者难以追赶** 的结构。

### 3.1 四层护城河

```
┌─────────────────────────────────────────────────────────┐
│  L4  品类话语权     ΔP / Pivotal / Gate 成为行业用语        │  ← 最难复制
├─────────────────────────────────────────────────────────┤
│  L3  数据飞轮       生产失败 trace → Case → 更准的门禁       │
├─────────────────────────────────────────────────────────┤
│  L2  工作流嵌入     required check / IDE 状态栏 / 审批流     │
├─────────────────────────────────────────────────────────┤
│  L1  技术内核       确定性 SCM · do() 传播 · Pivotal 归因    │  ← 起点
└─────────────────────────────────────────────────────────┘
```

| 层 | 现状 | 加深方式 | 复制难度 |
|---|---|---|---|
| **L1 技术内核** | 已实现，浏览器端完整 | 服务端同源、exact 覆盖率 ≥ 90% | 中：算法可被模仿，但工程细节多 |
| **L2 工作流嵌入** | CLI / Action / VS Code 雏形 | 成为 PR 默认 required check | 高：一旦嵌入，替换成本大 |
| **L3 数据飞轮** | `traceCaseSuggest` 已有，未接生产 | 生产日志管道 + 自动建议 Case | 很高：数据是私有且累积的 |
| **L4 品类话语权** | 内部使用术语 | 开放协议 + 技术写作 + 社区 | 最高：先定义者获得心智 |

### 3.2 关键洞察：确定性是护城河，不是限制

竞争者最自然的路径是「多跑几次 LLM 取统计」。这条路：

- **贵**：每次门禁 N 倍 token 成本
- **慢**：CI 里等不起
- **不可复现**：同一 PR 两次检查结果不同，工程师不会信任

OwnAgent 的 exact replay 路径在门禁场景下有 **成本、速度、可信度** 三重优势。战略上要坚持：**能确定性的地方绝不采样，采样的地方明确标注覆盖率**。

## 5. 路线图

### Horizon 1 · 敢用（2026 Q4 – 2027 Q1）

**主题**：把「能用」做成「敢用」——工程师愿意让它挡住自己的 PR。

| 优先级 | 里程碑 | 验收标准 |
|---|---|---|
| **P0** | 发版检查页重构落地 | 按 `plans/2026-09-30-release-check-replan.md` §7 的 7 条全部通过 |
| **P0** | 服务端同源 SCM | CLI / API 的 ΔP、pivotal 与浏览器结果一致（同输入同输出） |
| **P0** | PR 评论完整化 | Action 评论含 Verdict、ΔP、pivotal step、失败 case 明细 |
| **P1** | Exact 覆盖率仪表 | 内置 skill exact 覆盖率 ≥ 80%，不足时报告显式标注 |
| **P1** | Baseline 工作流 | staging / prod 基线可视化对比；发布自动 bump |
| **P2** | VS Code 插件上架 | Marketplace 可安装；状态栏显示 Gate 结果 |

**退出条件**：至少 1 个非本人维护的仓库，把 Skill Gate 设为 required check 并持续运行 4 周。

### Horizon 2 · 嵌入（2027 Q2 – Q4）

**主题**：从「工具」变成「流程」——团队的发布制度依赖它。

| 方向 | 关键交付 |
|---|---|
| **数据飞轮** | 生产 trace 接入协议；失败 trace 自动聚类 → 建议 Case → 一键入回归集 |
| **多 Skill 治理** | Skill 依赖图；路由 ambiguous 全局报告；一处改动影响哪些 Skill 的传播分析 |
| **策略即代码** | `.ownagent/policy.yml`：按 Skill 风险等级设定 WARN / BLOCK 阈值 |
| **审计合规** | 谁发布、哪版、门禁结果、是否 override、override 理由——可导出、可追溯 |
| **团队版** | 多用户、审批通知（飞书 / Slack / 邮件）、环境权限 |

**退出条件**：出现第一份引用 OwnAgent 门禁报告的真实事故复盘。

### Horizon 3 · 定义（2028）

**主题**：从「产品」变成「标准」。

| 方向 | 关键交付 |
|---|---|
| **开放协议** | `ownagent-check/2` 规范公开：Case 格式、Gate 输出、Pivotal 表达 |
| **OEM 嵌入** | 作为「Skill CI 模块」嵌入第三方 Agent 平台 |
| **私有化部署** | 企业内网完整部署，数据不出域 |
| **品类教育** | 技术白皮书、公开 benchmark、会议演讲 |

**退出条件**：至少一个第三方实现了开放协议的兼容输出。

## 6. 增长与市场进入（GTM）

### 6.1 目标用户分层

| 层级 | 画像 | 痛点 | 进入方式 |
|---|---|---|---|
| **种子** | 维护多个 SKILL.md 的独立开发者 / 开源项目 | 改了不知道会不会坏 | 免费 CLI + GitHub Action |
| **核心** | 5–50 人的 Agent 产品团队 | 多人改 Skill，互相踩；线上事故难追责 | 团队版 · 审批流 |
| **战略** | Agent 平台方（类 iMean） | 平台上第三方 Skill 质量不可控 | OEM 嵌入 |

### 6.2 增长引擎：开发者优先（Bottom-up）

```
开源 CLI / Action ──► PR 评论被团队看到 ──► 团队采用 required check
        ▲                                              │
        │                                              ▼
   技术写作 / 案例 ◄── 事故被拦住的真实故事 ◄── 团队版付费
```

**关键动作**：

1. **PR 评论即广告**：每条 Gate 评论是一次曝光，设计要让旁观者想点进来看。
2. **「被拦住的事故」叙事**：收集真实的「OwnAgent 挡住了一次坏发布」案例，这是最有说服力的内容。
3. **五分钟上手**：从 `npx ownagent check` 到看到第一份报告不超过五分钟。

### 6.3 商业模式（假设，待验证）

| 层 | 形态 | 价值锚点 |
|---|---|---|
| **Free** | CLI + Action + 本地 Web | 单人 / 开源永久免费 |
| **Team** | 托管服务 · 按席位 | 审批流、共享基线、通知、审计 |
| **Enterprise** | 私有化 · 年费 | 数据不出域、SSO、合规报告、SLA |
| **OEM** | 平台授权 · 按调用或年费 | 嵌入第三方 Agent 平台 |

> 定价在 Horizon 1 结束前不做决定。先验证「有人愿意让它挡 PR」，再验证「有人愿意为它付钱」。

## 7. 北极星指标与度量体系

### 7.1 北极星指标

> **每周被 Gate 检查的 Skill 变更数（Weekly Gated Changes）**

选它的理由：它同时反映了**采用广度**（多少仓库在用）、**嵌入深度**（是否每次改动都检查）和**信任度**（没人绕过它）。对话 DAU、页面 PV 都不是北极星。

### 7.2 分层指标

| 层 | 指标 | Horizon 1 目标 | Horizon 2 目标 |
|---|---|---|---|
| **采用** | 启用 Action 的外部仓库数 | ≥ 3 | ≥ 30 |
| **嵌入** | 设为 required check 的比例 | ≥ 30% | ≥ 60% |
| **信任** | BLOCK 后被 override 的比例 | 记录基线 | < 15% |
| **价值** | 被 BLOCK 且事后确认为真问题的比例（精确率） | 记录基线 | ≥ 80% |
| **飞轮** | 来自生产回流的 Case 占比 | — | ≥ 40% |
| **质量** | Exact 覆盖率 | ≥ 80% | ≥ 90% |

### 7.3 反指标（出现即报警）

- Override 比例持续上升 → 门禁噪音太大，工程师不信任
- 只看结构 diff、不看 ΔP / pivotal → 核心价值没被感知
- 产品被介绍成「带 SCM 的聊天 demo」→ 定位失败

## 8. 战略取舍：刻意不做

战略的本质是选择不做什么。

| 不做 | 原因 |
|---|---|
| **不做通用 Chat / RAG 产品** | 红海且商品化；对话保留为验收沙盒 |
| **不做 LLM-as-Judge 打分平台** | 与确定性路线冲突；市场已有成熟玩家 |
| **不做完整 Agent 开发框架** | 会与潜在 OEM 伙伴竞争；聚焦治理层 |
| **不为 demo 堆黑盒 UI** | 工程师信任来自可解释，不来自炫技 |
| **不在 H1 做多模型、多租户** | 先把单仓库单团队做到极致 |

## 9. 风险矩阵

| 风险 | 概率 | 影响 | 预警信号 | 应对 |
|---|---|---|---|---|
| **Skill 格式碎片化**，SKILL.md 未成为标准 | 中 | 高 | 主流平台推出互不兼容的 Skill 格式 | Semcompiler 做适配层；开放协议与格式解耦 |
| **大厂内置同类功能** | 中 | 高 | 主流 Agent 平台发布「Skill 测试」功能 | 加速 L2/L3 护城河；转 OEM 合作而非对抗 |
| **确定性覆盖率上不去**，mock 成本太高 | 中 | 中 | Exact 覆盖率长期 < 70% | Mock 工作台；从 trace 自动生成 mock |
| **门禁噪音过大**，工程师绕过 | 中 | 高 | Override 率 > 30% | 策略分级；WARN 默认不阻塞；精确率优先于召回率 |
| **个人项目带宽不足** | 高 | 高 | 路线图连续两个季度延期 | 严格按 §8 砍需求；H1 只做 P0 |

## 10. 作品集站点的角色

本仓库同时承载 **个人作品集** 与 **OwnAgent 产品**。两者关系应当明确：

| 维度 | 作品集 | OwnAgent |
|---|---|---|
| **目标** | 证明工程与产品能力 | 成为可独立使用的产品 |
| **受众** | 招聘方、合作方 | 维护 Skill 的开发团队 |
| **成功标准** | 访问者 5 分钟内理解「这人能做什么」 | 外部仓库持续运行 Gate |

**建议路径**：

1. **H1 期间**：保持同仓库，作品集把 OwnAgent 作为旗舰案例，首页直达「5 分钟发版路径」。
2. **H1 结束**：CLI / Action / 核心引擎拆为独立包（`@ownagent/core`、`@ownagent/cli`），作品集改为依赖它们。
3. **H2 起**：OwnAgent 拥有独立域名与文档站；作品集保留演示入口与技术叙事。

这样既不牺牲作品集的展示价值，也让产品不被「个人网站」的身份限制。

| 9–10 | 五分钟上手 | `npx` 一行命令出报告；README 重写为产品首页 |
| 11–12 | 寻找首批外部仓库 | 至少 3 个仓库接入；收集第一批反馈 |
| 13 | 季度复盘 | 对照 §7 指标；决定是否进入 H2 |

---

## 12. 结语

Agent 的下一阶段竞争，不在于谁的 Agent 更聪明，而在于 **谁的 Agent 改得更放心**。

OwnAgent 要做的，是让「这版能不能发」从一句凭感觉的判断，变成一份 **有因果、可复现、可追责** 的工程结论。

> **改这一步，后果会不会翻转 → 哪一步是根因 → 能不能合并。**
>
> 这句话讲清楚了，品类就立住了。
